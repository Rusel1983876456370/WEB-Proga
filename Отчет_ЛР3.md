## 1. Цель работы

Цель лабораторной работы — дополнить интерактивное приложение из лабораторной работы №2 серверной частью на Python, реализовать REST API и перенести постоянное хранение каталога в реляционную базу данных.

В ходе работы были реализованы связанные сущности «Запчасть» и «Категория», полный набор CRUD-операций, проверка данных на сервере, автоматическая документация OpenAPI и взаимодействие интерфейса с сервером через `fetch()`.

## 2. Постановка задачи

В качестве основы используется проект **«АвтоДеталь — каталог автозапчастей»**, разработанный в предыдущих лабораторных работах.

В ЛР2 данные сохранялись в `localStorage` конкретного браузера. В ЛР3 необходимо организовать общее серверное хранилище и получать каталог через HTTP-запросы.

Необходимо выполнить следующие задачи:

- выделить основную и связанную сущности предметной области;
- разработать backend на Python с использованием FastAPI;
- создать таблицы в SQLite и связать их внешним ключом;
- реализовать создание, чтение, изменение и удаление запчастей;
- добавить серверную валидацию и обработку ошибок;
- подключить frontend к API и сохранить функции ЛР2;
- сформировать документацию Swagger UI;
- проверить сохранение данных после перезапуска сервера.

Для работы с БД применяется SQLAlchemy, для проверки JSON — Pydantic, для запуска приложения — Uvicorn.

## 5. Архитектура приложения

Приложение разделено на клиентскую и серверную части. Браузер отображает каталог и отправляет HTTP-запросы. FastAPI принимает запросы, проверяет данные и вызывает функции работы с БД. SQLAlchemy выполняет операции в SQLite.

Например, при добавлении детали выполняются следующие действия:

1. Пользователь заполняет форму в браузере.
2. JavaScript проверяет поля и отправляет JSON методом `POST`.
3. Pydantic проверяет типы и ограничения данных.
4. SQLAlchemy создаёт запись и фиксирует транзакцию.
5. Сервер возвращает созданный объект с кодом `201`.
6. Frontend обновляет `state.items` и перерисовывает каталог.

В основном режиме один сервер на порту `8000` обслуживает и интерфейс, и API. Дополнительно предусмотрен отдельный frontend на порту `5500`; для него настроен CORS.

## 6. Сущности предметной области

Основная сущность — **запчасть** (`Part`), связанная — **категория** (`Category`). Одной категории соответствует несколько запчастей. Каждая запчасть относится к одной категории.

Таблица `categories`:

| Поле | Тип SQLAlchemy | Назначение |
|---|---|---|
| `id` | `Integer` | Первичный ключ |
| `name` | `String(60)` | Уникальное название категории |
| `slug` | `String(30)` | Уникальное символьное обозначение |

Таблица `parts`:

| Поле | Тип SQLAlchemy | Назначение |
|---|---|---|
| `id` | `Integer` | Первичный ключ |
| `name` | `String(60)` | Название запчасти |
| `description` | `Text` | Описание |
| `article` | `String(20)` | Уникальный артикул |
| `price` | `Numeric(10, 2)` | Цена в рублях |
| `category_id` | `Integer`, FK | Ссылка на категорию |
| `parameter` | `String(120)` | Техническая характеристика |
| `image_url` | `String(100)` | Путь к изображению |
| `created_at` | `DateTime` | Дата и время создания |

Для поля `category_id` установлен внешний ключ на `categories.id`. Удаление категории, на которую ссылаются запчасти, ограничивается правилом `RESTRICT`.

## 7. Подключение к базе данных

Настройки соединения размещены в `backend/app/database.py`. По умолчанию используется файл `data/autodetal.db`. Путь вычисляется относительно проекта и не зависит от текущей папки терминала.

Фрагмент настройки сессий:

```python
engine = make_engine(DATABASE_URL)
SessionLocal = sessionmaker(bind=engine, expire_on_commit=False)

def get_db():
    with SessionLocal() as session:
        yield session
```

Для SQLite при каждом новом соединении включается проверка внешних ключей:

```python
cursor.execute("PRAGMA foreign_keys=ON")
```

FastAPI получает сессию через зависимость `Depends(get_db)`. После обработки запроса контекстный менеджер закрывает сессию.

## 8. Модели и ограничения базы данных

Таблицы описаны классами SQLAlchemy в `models.py`. Ниже приведён фрагмент модели запчасти:

```python
id: Mapped[int] = mapped_column(Integer, primary_key=True)
name: Mapped[str] = mapped_column(String(60), nullable=False)
article: Mapped[str] = mapped_column(
    String(20), unique=True, nullable=False
)
price: Mapped[Decimal] = mapped_column(Numeric(10, 2), nullable=False)
category_id: Mapped[int] = mapped_column(
    ForeignKey("categories.id", ondelete="RESTRICT"),
    nullable=False, index=True
)
```

Обязательные поля имеют ограничение `NOT NULL`. Для артикула задана уникальность. Ограничения `CHECK` проверяют длину названия и описания, диапазон цены, точность до копеек и допустимые пути изображений.

Связь моделей задаётся через `relationship()`:

```python
# В модели Category
parts: Mapped[list["Part"]] = relationship(back_populates="category")

# В модели Part
category: Mapped[Category] = relationship(
    back_populates="parts", lazy="joined"
)
```

При получении запчасти в ответ включается вложенный объект категории. Операции выполняются через ORM без склеивания SQL-запросов с пользовательскими значениями.

## 9. Создание таблиц и начальные данные

При запуске FastAPI вызывается `init_db(engine)`. Таблицы создаются командой:

```python
Base.metadata.create_all(engine)
```

Затем проверяется наличие категорий:

```python
if db.scalar(select(func.count()).select_from(Category)):
    return
```

Если категории уже существуют, повторное заполнение не выполняется. Поэтому удалённые пользователем детали не появляются снова после перезапуска.

Для новой БД создаются шесть категорий: «Двигатель», «Тормоза», «Зажигание», «Подвеска», «Привод» и «Другое». Исходный каталог содержит шесть деталей: масляный фильтр, тормозной диск, свечу зажигания, воздушный фильтр, амортизатор и поликлиновой ремень.

В поставленной с проектом демонстрационной БД дополнительно сохранена запись, созданная через API при проверке. Первичную инициализацию можно выполнить отдельно:

```bash
python -m scripts.init_db
```

Для текущей схемы используется `create_all()`. Автоматические миграции существующих таблиц в этой версии не реализованы.

## 10. Серверная валидация данных

Входные данные проверяются моделями Pydantic: `PartCreate` для создания и `PartUpdate` для изменения. Модель `PartRead` задаёт формат ответа.

Основные ограничения:

| Поле | Проверка |
|---|---|
| `name` | От 3 до 60 символов |
| `description` | От 10 до 240 символов |
| `article` | От 4 до 20 символов, буквы, цифры и дефис |
| `price` | От 1 до 1 000 000 рублей, не более двух десятичных знаков |
| `category_id` | Положительное целое число и существующая категория |
| `parameter` | Не более 120 символов |
| `image_url` | Один из шести разрешённых путей SVG |

Перед проверкой артикула удаляются пробелы по краям, а буквы приводятся к верхнему регистру:

```python
@field_validator("article", mode="before", check_fields=False)
    @classmethod
    def normalize_article(cls, value):
        return value.strip().upper() if isinstance(value, str) else value
```

Неизвестные поля запрещены настройкой `extra="forbid"`. При `PATCH` отсутствующие поля сохраняют прежнее значение; явное `null` отклоняется.

Цена обрабатывается как `Decimal`. Frontend передаёт её десятичной строкой, и сервер также возвращает её строкой. В SQLite используется числовая аффинность, поэтому дополнительно проверяется допустимая точность цены.

## 12. Получение списка и отдельной детали

Список запчастей выбирается из БД с сортировкой по идентификатору:

```python
def get_parts(db: Session):
    return db.scalars(select(Part).order_by(Part.id)).all()
```

Получение отдельной записи:

```python
def get_part(db: Session, part_id: int):
    part = db.get(Part, part_id)
    if part is None:
        raise HTTPException(404, "Запчасть не найдена")
    return part
```

Если запчасть существует, сервер возвращает объект с кодом `200`. Если запись отсутствует, возвращается `404` и сообщение «Запчасть не найдена».

Поиск, фильтрация и сортировка каталога выполняются на клиенте над уже загруженным списком. В этой реализации API не принимает параметры поиска и пагинации.

## 13. Создание новой запчасти

Кнопка «Добавить деталь» открывает форму. После клиентской проверки frontend отправляет `POST /api/parts`.

Пример тела запроса с новым уникальным артикулом:

```json
{
  "name": "Салонный фильтр",
  "description": "Очищает воздух в салоне автомобиля от пыли.",
  "article": "AP-CB-008",
  "price": "790.50",
  "category_id": 1,
  "parameter": "Угольный, 200 × 180 мм",
  "image_url": "/assets/images/filter.svg"
}
```

Серверная функция создания:

```python
def create_part(db: Session, data):
    require_category(db, data.category_id)
    part = Part(**data.model_dump())
    db.add(part)
    commit(db)
    db.refresh(part)
    return part
```

Сначала проверяется существование категории. Затем создаётся объект модели, добавляется в сессию и сохраняется через `commit()`. Вызов `refresh()` получает актуальные поля из БД.

Ответ имеет код `201 Created`, содержит созданную запчасть и заголовок `Location` с её адресом. Идентификатор назначается БД; frontend использует значение из ответа.

## 14. Редактирование запчасти

На карточку добавлена кнопка «Изменить». При нажатии выполняется `GET /api/parts/{id}`, а полученные значения подставляются в модальную форму.

Для сохранения используется `PATCH /api/parts/{id}`. Например, изменение только цены:

```json
{"price": "849.90"}
```

Серверная функция обновления:

```python
def update_part(db: Session, part: Part, data):
    changes = data.model_dump(exclude_unset=True)
    if not changes:
        raise HTTPException(400, "Укажите хотя бы одно поле для изменения")
    if "category_id" in changes:
        require_category(db, changes["category_id"])
    for field, value in changes.items():
        setattr(part, field, value)
    commit(db)
    db.refresh(part)
    return part
```

Параметр `exclude_unset=True` исключает поля, которые клиент не передал. Пустой объект изменения возвращает ошибку `400`. При изменении категории повторно проверяется её наличие.

После ответа `200` frontend заменяет соответствующий объект в `state.items` и вызывает `render()`.

## 15. Удаление запчасти и транзакции

Удаление выполняется после подтверждения пользователем. Frontend отправляет `DELETE /api/parts/{id}`.

Функция работы с БД:

```python
def delete_part(db: Session, part: Part):
    db.delete(part)
    commit(db)
```

После успешного удаления сервер отвечает `204 No Content`. Только после этого frontend исключает карточку из состояния. Последующее обращение по удалённому ID возвращает `404`.

Создание, изменение и удаление используют общий механизм фиксации транзакции:

```python
def commit(db: Session):
    try:
        db.commit()
    except IntegrityError:
        db.rollback()
        raise HTTPException(400, "Нарушено ограничение БД. Артикул должен быть уникальным.") from None
```

При нарушении ограничения БД вызывается `rollback()`. Например, повторяющийся артикул не сохраняется, а клиент получает ошибку `400`.

## 16. Взаимодействие frontend с сервером

В `frontend/js/app.js` используется единый объект состояния:

```javascript
const state = {
  items: [], categories: [],
  searchQuery: '', selectedCategory: 'all', sortBy: 'name-asc',
  loading: false, busy: false, editingId: null, connected: false
};
```

`items` содержит загруженные запчасти, `categories` — справочник категорий. Флаги `loading` и `busy` управляют состоянием загрузки и блокировкой повторных действий, `editingId` хранит ID редактируемой записи.

Каталог и категории запрашиваются при запуске:

```javascript
const [categories, items] = await Promise.all([
  api('/api/categories'), api('/api/parts')
]);
state.categories = categories;
state.items = items;
state.connected = true;
fillCategories();
```

Функция `api()` оборачивает `fetch()`: добавляет `Content-Type` при отправке JSON, проверяет `response.ok`, разбирает ответ и обрабатывает ошибки. Для ответа `204` JSON не разбирается:

```javascript
return response.status === 204 ? null : await response.json();
```

Один обработчик формы используется для создания и редактирования:

```javascript
const item = await api(
  editingId ? `/api/parts/${editingId}` : '/api/parts',
  {
    method: editingId ? 'PATCH' : 'POST',
    body: JSON.stringify(data)
  }
);
```

После ответа обновляется состояние и вызывается `render()`. Пользовательский текст выводится через `textContent`. Источником постоянных данных является SQLite; массив `state.items` служит текущим представлением каталога в браузере.

## 17. OpenAPI и Swagger UI

FastAPI автоматически формирует спецификацию API на основании маршрутов, типов и Pydantic-моделей.

| Адрес | Назначение |
|---|---|
| `/docs` | Интерактивная документация Swagger UI |
| `/openapi.json` | Машиночитаемая спецификация OpenAPI |
| `/redoc` | Дополнительное представление документации |

Для Swagger UI JavaScript и CSS включены в проект в `backend/static/swagger/`. Для этой страницы не требуется загрузка ресурсов с внешнего CDN.

Проверка запроса через Swagger:

1. Открыть `http://127.0.0.1:8000/docs`.
2. Развернуть нужный метод, например `GET /api/parts`.
3. Нажать «Try it out», затем «Execute».
4. Проверить код ответа и JSON.
5. Аналогично выполнить `POST`, сохранить полученный ID и использовать его в `PATCH` и `DELETE`.

Документация показывает обязательные поля, ограничения и схемы ответов. Адреса `/redoc` и `/openapi.json` зарегистрированы отдельно от frontend.

| Документация | OpenAPI и Swagger UI |
| Подключение frontend | HTTP-запросы через `fetch()` |
| Постоянное хранение | Файл `data/autodetal.db` |
| Сохранение функций ЛР2 | Поиск, категории, сортировка и модальное окно |

Ошибки обрабатываются явно: `400` — некорректный JSON, повторный артикул, несуществующая категория или пустое изменение; `404` — отсутствие записи; `422` — ошибка схемы данных; `500` — внутренняя ошибка сервера.

При сетевой ошибке интерфейс выводит сообщение и предлагает обновить каталог. Запрос ограничен тайм-аутом 10 секунд. Во время сохранения поля формы блокируются.

Для передачи исходников подготовлен локальный Git-репозиторий `autodetal-lab3.bundle` с историей ЛР2 → ЛР3. Удалённая публикация выполняется по инструкции в README; адрес GitHub/GitLab в исходных материалах не указан.

## 20. Запуск проекта

Для работы требуется Python 3.10 или новее. В Windows можно запустить `start.bat`. При ручном запуске необходимо открыть терминал в корне проекта.

Создание виртуального окружения:

```bash
python -m venv .venv
```

Активация в командной строке Windows:

```bat
.venv\Scripts\activate.bat
```

В Linux и macOS:

```bash
source .venv/bin/activate
```

Установка зависимостей и запуск:

```bash
python -m pip install -r backend/requirements.txt
python -m uvicorn backend.app.main:app --reload --host 127.0.0.1 --port 8000
```

После запуска открыть:

- каталог: `http://127.0.0.1:8000`;
- Swagger UI: `http://127.0.0.1:8000/docs`;
- проверка сервера: `http://127.0.0.1:8000/api/health`.

Отдельная установка сервера БД не требуется. Таблицы создаются автоматически. Для просмотра записей:

```bash
python scripts/inspect_db.py
```

Остановка Uvicorn выполняется сочетанием клавиш `Ctrl + C`. После повторного запуска используется тот же файл SQLite, поэтому изменения сохраняются.
