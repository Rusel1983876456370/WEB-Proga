# АвтоДеталь — лабораторная работа №3

**Тема:** каталог автозапчастей. **Работа:** Backend с REST API и базой данных.

Проект продолжает ЛР2: сохранены оформление, SVG-иллюстрации, поиск, фильтрация,
сортировка, модальная форма и State-Driven UI. Каталог больше не хранится в
localStorage: источник данных — SQLite, доступная через REST API FastAPI.
Добавлено редактирование всех полей запчасти и получение одной записи по ID.

## Быстрый запуск на Windows

1. Установите Python **3.10 или новее** с python.org (при установке включите Python Launcher и Add Python to PATH).
2. Распакуйте архив полностью. Не запускайте файлы прямо внутри ZIP.
3. Запустите **start.bat**. При первом запуске нужен интернет для установки библиотек.
4. Дождитесь сообщения `Uvicorn running on http://127.0.0.1:8000`.
5. Откройте **http://127.0.0.1:8000**. Для API: **http://127.0.0.1:8000/docs**.
6. Окно сервера оставьте открытым. Остановка — Ctrl+C.

Frontend и backend запускаются одним сервером. Не открывайте index.html двойным
щелчком: при file:// API-запросы не попадут на backend.

Linux/macOS: `bash start.sh`.
Проверенная среда: Python 3.12, Linux. Windows-скрипт включён для удобства;
его отдельный запуск на Windows в рамках проверки не выполнялся.

## Стек

Python 3.10+, FastAPI 0.162.0, SQLAlchemy 2.1.6, Pydantic 2.14.2,

## Сущности и отношения

Основная сущность — **Part (Запчасть)**, таблица `parts`.
Связанная — **Category (Категория)**, таблица `categories`.
Отношение: одна категория содержит много деталей (1:N).
Внешний ключ: `parts.category_id → categories.id`, удаление используемой категории запрещено.

| Поле Part | Тип | Назначение и ограничения |
|---|---|---|
| id | INTEGER | Первичный ключ, генерируется БД |
| name | VARCHAR(60) | Название, NOT NULL, 3–60 символов после trim |
| description | TEXT | Описание, NOT NULL, 10–240 символов |
| article | VARCHAR(20) | Артикул, UNIQUE, NOT NULL; API: 4–20 букв/цифр/дефисов, приводится к верхнему регистру |
| price | NUMERIC(10,2) | Цена в ₽, NOT NULL, CHECK: 1…1 000 000, до 2 десятичных знаков |
| category_id | INTEGER | NOT NULL, FOREIGN KEY, индекс |
| parameter | VARCHAR(120) | Характеристика; по умолчанию «Добавлено пользователем» |
| image_url | VARCHAR(100) | Локальная иллюстрация, одна из 6 допустимых SVG |
| created_at | DATETIME | Время создания; API возвращает UTC |

Category: `id` INTEGER PRIMARY KEY, `name` VARCHAR(60) NOT NULL UNIQUE,
`slug` VARCHAR(30) NOT NULL UNIQUE; CHECK на длины строк.
В PartRead дополнительно возвращается вложенный объект `category`.
Цена сериализуется в JSON строкой, например `"790.50"`, чтобы сохранить десятичное представление.
SQLite применяет affinity NUMERIC, а не тип decimal с фиксированной точностью;
API проверяет число копеек, CHECK дополнительно отвергает дробные копейки,
SQLAlchemy читает цену как Decimal. В учебном проекте не выполняются финансовые расчёты.

## REST API

| Метод | Endpoint | Действие | Успех |
|---|---|---|---|
| GET | /api/parts | Список деталей | 200 |
| POST | /api/parts | Создание | 201 + Location |
| GET | /api/parts/{part_id} | Деталь по ID | 200 |
| PATCH | /api/parts/{part_id} | Частичное обновление | 200 |
| DELETE | /api/parts/{part_id} | Удаление | 204 без тела |
| GET | /api/categories | Справочник категорий | 200 |
| GET | /api/categories/{category_id} | Категория по ID | 200 |
| GET | /api/health | Доступность сервера и БД | 200 |

Ошибки: 400 — повторяющийся артикул, несуществующая категория, пустой PATCH,
повреждённый JSON; 404 — запись отсутствует; 422 — валидация полей или ID;
500 — внутренняя ошибка (SQL и настройки клиенту не раскрываются).
При неудачной транзакции выполняется rollback.
Неизвестные поля запросов и явный null в PATCH запрещены.
Пропущенное поле PATCH сохраняет прежнее значение.

Документация генерируется автоматически из маршрутов и Pydantic:
- Swagger UI: http://127.0.0.1:8000/docs (ресурсы включены в backend/static/swagger, CDN не нужен).
- ReDoc: http://127.0.0.1:8000/redoc (для загрузки интерфейса нужен доступ к CDN).
- JSON: http://127.0.0.1:8000/openapi.json.
- Снимок спецификации: `docs/openapi.json`.

## Ручной запуск

Из **корневой папки autodetal-lab3**:

```powershell
py -3 -m venv .venv
.venv\Scripts\python.exe -m pip install -r backend/requirements.txt
.venv\Scripts\python.exe -m uvicorn backend.app.main:app --reload
```

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements.txt
.venv/bin/python -m uvicorn backend.app.main:app --reload
```

### Запуск БД

Отдельный сервер БД не нужен. При первом запуске backend создаёт
`data/autodetal.db`, 6 категорий и 6 исходных деталей из ЛР2.
В архиве уже есть БД с исходными данными и одной демонстрационной записью,
созданной через HTTP API при проверке. Она видна на скриншотах.
Последующие запуски сохраняют изменения. Даже при удалении всех деталей
они не восстанавливаются при перезапуске: заполнение выполняется только
когда справочник категорий ещё пуст.

Создать БД отдельно: `python -m scripts.init_db` (из активированной .venv).
Просмотр реальных строк SQL: `python scripts/inspect_db.py`.
HTML-вывод SELECT: `python scripts/inspect_db.py --html docs/database-view.html`.
Графический просмотр: откройте `data/autodetal.db` в DB Browser for SQLite,
вкладка Browse Data → таблица parts. Закройте редактор перед изменением данных.

Для нового чистого набора: остановите сервер, сделайте копию `data/autodetal.db`,
затем удалите рабочий файл и запустите backend — появятся 6 исходных деталей.

### Запуск frontend

**Основной способ:** откройте http://127.0.0.1:8000 — HTML, CSS, JS и API
выдаёт один FastAPI-сервер.

**Необязательный раздельный способ:** во втором терминале:

```bash
cd frontend
python -m http.server 5500 --bind 127.0.0.1
```

Откройте http://127.0.0.1:5500. Backend продолжает работать на порту 8000.
В JS для порта 5500 выбран API http://127.0.0.1:8000.
CORS разрешает только http://127.0.0.1:5500 и http://localhost:5500.
При изменении списка адресов скопируйте `.env.example` в `.env` и настройте CORS_ORIGINS.
`.env` исключён из Git. Файл SQLite тоже исключён из Git; создаётся при запуске.

## Примеры запросов

Самый простой способ без терминала: `/docs` → нужный метод → **Try it out**
→ заполнить поля → **Execute**.

Пример POST (артикул должен быть новым):

```json
{
  "name": "Салонный фильтр",
  "description": "Очищает воздух в салоне автомобиля от пыли.",
  "article": "AP-CB-008",
  "price": "790.50",
  "category_id": 1,
  "parameter": "Угольный, 200 × 180 мм",
  "image_url": "/assets/images/filter.svg"
}
```

POST /api/parts возвращает 201 и созданную запись. Для PATCH /api/parts/ID:

```json
{"price": "849.90"}
```

DELETE /api/parts/ID возвращает 204. GET этого же ID после удаления — 404.
ID берите из ответа POST, не подставляйте заранее угаданный номер.
Готовый исполняемый пример HTTP-клиента: `python scripts/demo_api.py`
(backend должен работать; сценарий создаёт, меняет и удаляет только свою новую запись).

```bash

python -m pytest -q
```

Интеграционные тесты работают с отдельной временной SQLite.
Проверяются CRUD, ограничения БД и FK, ошибки, нормализация и уникальность
артикулов, CORS, OpenAPI, откат транзакций, сохранение между двумя процессами

## Структура

- `backend/app/main.py` — приложение, CORS, ошибки, документация, раздача frontend.
- `backend/app/database.py` — соединение, сессии, внешние ключи SQLite.
- `backend/app/models.py` — таблицы, типы и ограничения SQLAlchemy.
- `backend/app/schemas.py` — валидация и схемы OpenAPI.
- `backend/app/crud.py` — работа с БД.
- `backend/app/routers/` — HTTP-маршруты деталей и категорий.
- `backend/app/seed.py` — создание схемы и первичные данные.
- `frontend/` — адаптированный сайт ЛР2, без второго дубликата app.js.
- `scripts/` — инициализация, просмотр БД, воспроизводимый пример API.
- `tests/` — автоматические интеграционные тесты.
- `data/autodetal.db` — готовая демонстрационная SQLite в ZIP, не в Git.
- `docs/` — методичка, отчёт, доказательства проверки и инструкция по защите.

Миграции Alembic в методичке приведены в рекомендуемой структуре,
но не входят в минимальные требования. Для этой версии используется
Base.metadata.create_all; изменение существующей схемы требует миграции
или пересоздания учебной БД с резервной копией.

## Git-репозиторий

Исходный ZIP не содержит адреса удалённого репозитория. Удалённая публикация
не выполнена. В архив вложен `autodetal-lab3.bundle` — локальный Git-репозиторий
с историей ЛР2 → ЛР3 (автоматические данные БД исключены).

Восстановление:

```bash
git clone autodetal-lab3.bundle autodetal-lab3-git
cd autodetal-lab3-git
```

Создайте пустой репозиторий в своём GitHub/GitLab, затем используйте **его настоящий URL**:

```bash
git remote remove origin
git remote add origin <URL_ВАШЕГО_РЕПОЗИТОРИЯ>
git push -u origin main
```

Угловые скобки заменяются вместе с содержимым. В README или форму сдачи
вставьте полученный адрес своего репозитория.

## Границы учебного приложения

Сервер рассчитан на локальный запуск (127.0.0.1), аутентификация не добавлялась:
она не требуется ЛР3. Все клиенты этого сервера работают с одним каталогом.
Поиск, фильтрация и сортировка выполняются в JS над загруженным списком;
создание, чтение, обновление и удаление данных выполняются API и БД.
Данные из localStorage прошлых запусков ЛР2 автоматически не импортируются.
